# RE팀 업무 기록 — 팀 지식 레포 (opt-in)

개인 업무일지를 팀 공용 git 레포("RE팀 업무 기록")로 흘려보내, 팀원(과 그 에이전트)이 `/bc-knowledge` 스킬 하나로 조회하게 합니다.

레포에는 **성격이 다른 두 개의 면**이 있습니다.

| 면 | 무엇 | 시간 축 | 만드는 것 |
|---|---|---|---|
| `activity/<사람>/<프로젝트>/<날짜>.md` | 일지 원문 미러 — 누가·언제·무엇을 | **시계열** (사람별) | `sync-activity.sh` (일지 기록 직후, 결정론적) |
| `cards/<슬러그>.md` | 증류된 트러블슈팅 지식 | **무시간** (원인별 병합) | `extract-knowledge.sh` (주 1회, LLM) |

두 면을 분리한 이유: "A가 어디까지 했나"는 **시간 순서**가 답이고, "이 에러 선례 있나"는 **원인별 병합**이 답입니다. 한 자료구조로 둘 다 하려면 한쪽이 망가집니다.

## 이 레포는 사내 내부용입니다 — 익명화하지 않습니다

고객명·서버 주소·사번·내부 URL·담당자 이름을 **그대로** 적습니다. 가려 쓰면 다음 담당자가 카드를 못 씁니다. 작성자 귀속(`sources`의 `<작성자> · <프로젝트> · <날짜> · <세션ID>`)도 의도적으로 남깁니다 — 요구사항상 "누가 했나"가 조회 대상입니다.

**단 하나의 예외는 자격증명입니다.** git 히스토리에 들어간 API 키는 회수할 수 없으므로 `apply-knowledge.py`가 결정론적으로 차단합니다(fail-closed, 아래 참조). 변수명 언급(`FLASK_SECRET_KEY가 불일치`)은 무방하고, **값**만 금지입니다.

> 외부(고객·공개) 배포용으로 이 레포 내용을 쓸 때는 사람이 한 번 걸러야 합니다. `/bc-knowledge` 스킬이 그 경고를 띄웁니다.

## 코어 파이프라인과의 관계

**완전 opt-in**입니다. `config.json`에 `knowledge_repo`가 없으면 activity 동기화도 지식 추출도 동작하지 않고, 일지 기록 코어(훅→요약→라우팅→기록)는 그대로입니다.

## 구성 요소

| 파일 | 역할 |
|---|---|
| `install-knowledge.sh` | opt-in 설치기 — config 기록, 레포 스캐폴드, `/bc-knowledge` 스킬 설치 |
| `scripts/core/sync-activity.sh` | 일지 → `activity/` 미러 (LLM 없음, 증분, 시간당 1회 push) |
| `scripts/core/build-activity-index.py` | `activity/INDEX.md` 재생성 (기간 전수 열람용) |
| `scripts/core/rebuild-daily-index.py` | 유지보수 — `_daily`를 프로젝트 일지에서 재생성 |
| `scripts/core/extract-knowledge.sh` | 주간 지식 추출 배치 — **2단계** (triage → 세션별 카드) |
| `scripts/core/filter-transcript.py` | 세션 트랜스크립트(수십 MB)를 근거 60KB로 압축 |
| `scripts/core/apply-knowledge.py` | 추출 출력 파싱·적용 + 자격증명 게이트 + INDEX 재생성 |
| `skills/bc-knowledge/SKILL.md` | 조회 스킬 (활동 질의 / 기술 질의 / 리포트 라우팅) |

## 설치

```bash
bash install-knowledge.sh --repo ~/re-team-work-log
git -C ~/re-team-work-log remote add origin <팀 공용 레포 URL>   # 팀 공유 시
bash scripts/core/sync-activity.sh --all                        # 기존 일지 백필
```

주간 추출은 자동 등록하지 않습니다 — **수동** / **launchd**(macOS 주 1회) / **cloud 루틴** 중 선택.

## activity 동기화 (요구사항 ①②)

- `journals/<프로젝트>/<날짜>.md` → `activity/<작성자>/<프로젝트>/<날짜>.md`
- `journals/_daily/<날짜>.md` → `activity/<작성자>/_daily/<날짜>.md` (그날의 프로젝트 횡단 요약)
- 작성자는 config의 `author` → git `user.name` → `$USER` 순으로 결정, 공백/슬래시는 `_`로 치환
- **`private/`는 절대 읽지 않습니다** (테스트로 고정) — 소스는 `journals/`뿐
- 일지 기록(`write-entry.sh`) 직후 백그라운드로 증분 실행. 커밋은 매번, **push는 시간당 최대 1회**(`.git/.activity-last-push`)로 스로틀
- LLM을 쓰지 않습니다. 요약은 이미 일지에 있고, 미러링은 결정론적 작업입니다.

### `activity/INDEX.md` — 폴더명은 고객이 아니다

`sync-activity.sh`가 매 실행마다 `activity/INDEX.md`를 재생성합니다: **(날짜 · 시각 · 사람 · 프로젝트 · 제목 · 세션ID) 한 줄씩.**

있어야 하는 이유는 하나입니다. **디렉토리 이름은 작업 당시 cwd의 레포명이지 고객명이 아닙니다.** 실측 7월에 SKT 작업은 `zez-server`(11세션)·`agent-runtime`(4)에 `skt-*`(17)만큼 들어 있었고, `skt-*`로 필터하면 관련 파일 35개 중 17개만 잡히면서 **누락이 결과에 드러나지 않습니다** — 리포트가 완성된 것처럼 보입니다.

해법은 더 똑똑한 필터가 아니라 **전수 열람을 싸게 만드는 것**입니다. 날짜 접두로 grep 한 번(`grep '| 2026-07-' INDEX.md`)이면 그 기간 전 세션이 제목과 함께 나오므로, 폴더명으로 추측하는 대신 제목을 보고 대상을 고른 뒤 필요한 파일만 엽니다.

고객 축에 가장 가까운 신호는 **워크스페이스 열**입니다 — 일지 푸터의 `cwd:`에서 프로젝트 체크아웃을 담은 상위 디렉토리를 뽑습니다. 실측에서 `skt-*` 폴더 필터는 18건, `skt-agent-proj` 워크스페이스는 29건을 잡았습니다. 다만 힌트일 뿐입니다: 반대로 그 안에 무관한 작업이 섞이기도 하므로 최종 판단은 제목으로 합니다.

세션 열은 **Claude Code 세션 ID이지 작업 단위가 아닙니다.** resume으로 몇 주씩 이어져 한 ID가 수십 행에 걸치므로(실측: 한 세션이 26일·20행), **같은 날 + 같은 주제**일 때만 한 건으로 묶습니다.

제목이 깨진 옛 기록(요약 포맷 화이트리스트 도입 이전, CLI 에러 문구가 제목 자리에 박힌 것)은 드롭하지 않고 `(제목 없음 — 기록 손상)`으로 표시합니다. 조용한 누락이 가장 위험합니다.

### 진척 조회

"A가 어디까지 진행했나"는 프로젝트 폴더부터 열면 안 됩니다 — 한 세션이 여러 프로젝트 디렉토리에 걸치는 일이 흔해서(작업 중 `cd`) 한 폴더만 보면 같은 업무의 절반을 놓칩니다. **주제어로 `grep -ril` 먼저**, 걸린 파일을 날짜순으로 읽고 **마지막 날짜의 `Next`가 남은 일**입니다. 단 `Next`는 다음 세션으로 이월되지 않으므로, **최신 파일에 그 주제가 없다고 끝난 게 아닙니다** — 그 주제가 마지막으로 언급된 날짜까지 거슬러 올라가야 합니다. 완료 여부는 같은 주제 카드의 `## 검증 상태`가 유일한 근거일 때가 많습니다.

진척은 퍼센트가 아니라 서술형입니다.

### `_daily`의 키는 (세션, 프로젝트)

`_daily/<날짜>.md`는 세션 하나가 아니라 **(세션 × 프로젝트)마다 한 줄**입니다. 세션 ID만으로 키를 잡던 초기 구현에서는 한 세션이 프로젝트를 옮길 때 뒤 항목이 앞 항목을 덮어써서, 실측 22일 중 9일의 기록이 조용히 사라졌습니다(전체 항목의 26%). 구 포맷 마커는 다음 쓰기 때 자동 승격되고, 이미 유실된 과거분은 `rebuild-daily-index.py`로 프로젝트 일지에서 복구합니다.

## 지식 추출 — 왜 2단계인가

일지 bullet은 평균 63자입니다. "FLASK_SECRET_KEY 불일치 확정"은 남지만 **후보 8개를 어떻게 하나씩 소거했는지**는 일지에 없습니다. 그런데 그게 다른 팀원에게 가장 값진 부분입니다. 원본은 세션 트랜스크립트에만 있습니다.

```
1단계 TRIAGE   변경된 일지 전체 → LLM 1콜 → "카드감 세션 목록 + 주제 + 검색 키워드 + deep 여부"
2단계 CARDS    세션 하나당 LLM 1콜 → 그 세션이 낳는 카드 전부
               deep=yes이고 트랜스크립트가 있으면 filter-transcript.py의 60KB 근거를 입력으로,
               아니면 그 세션의 일지로 폴백
```

- **카드당이 아니라 세션당 1콜**입니다. 카드 3장을 낳는 세션도 트랜스크립트를 한 번만 보냅니다.
- 트랜스크립트 위치는 세션 ID로 전역 탐색합니다(`find ~/.claude/projects -name "<세션ID>.jsonl"`) — 일지의 cwd와 트랜스크립트 디렉토리 인코딩이 항상 일치하지는 않기 때문입니다.
- 트랜스크립트가 없으면(정리됨·다른 머신) **일지 폴백**으로 조용히 낮춰 실행합니다. 카드는 나오되 얕아집니다.
- 실측 비용: 1단계 ~15k + 2단계 세션당 ~20k 토큰. 주당 6세션 기준 ≈ 135k 토큰 ≈ $0.7/주/인.

### filter-transcript.py

수십 MB 트랜스크립트에서 **결론이 적히는 곳**(user 턴 + assistant 텍스트)만 남기고 attachment·tool_use·tool_result·thinking(측정상 ~85%)을 버린 뒤, 점수 상위부터 예산(기본 60KB)까지 채우고 시간순으로 복원합니다.

```
score = 진단 키워드 + 3×판정어(원인/확정/소거…) + 5×주제어
```

**주제어(`--topic`)가 결정적입니다.** 긴 세션은 며칠에 걸쳐 여러 문제를 넘나들기 때문에 "뒤에서부터 자르기"는 가장 최근 주제만 집습니다 — 실측 32MB 세션에서 그 방식은 카드 주제의 근거를 **0건** 반환했습니다. 주제어는 1단계 triage가 알고 있으므로 넘겨줍니다. 같은 입력 → 같은 출력(결정론적)이라 재시도가 프롬프트 캐시를 재사용합니다.

## 지식 카드

- 위치: `<knowledge_repo>/cards/*.md` — **플랫 구조** (다차원 검색은 frontmatter 태그로)
- 포맷: frontmatter(`tags`, `sources`) + **문제상황 → 시도 → 해결 → 검증 상태 → 정리** (+ 재발 시 `## 사례` 누적)
- `INDEX.md`: 결정론적 자동 생성 (직접 편집 금지) / `excluded.md`: 경계 규칙 제외 항목의 감사 추적

### 카드 품질 규칙 (추출 프롬프트가 강제)

페르소나 검색 테스트(다른 프로젝트 팀원이 실제로 겪는 문제로 검색)로 검증된 기준:

- **자족성 (죽은 포인터 금지)**: 팀원은 원천 세션을 열지 않는다. "출처 세션 참조"로 끝내지 말고 확인 방법·결과·수치·명령·로그 문구를 본문에 담는다. 후보 배제 과정이 있으면 **표**로.
- **`## 검증 상태`**: `검증됨` / `방향만 정리(적용 미검증)` / `진단만(해결 미도출)` — 열지 않고도 신뢰도를 안다.
- **벤더/도구명 태그**: 본문이 일반어("OCR 업스트림")여도 tags에 벤더명(Upstage 등)을 넣는다. 팀원은 벤더명으로 검색한다.
- **정직성**: 자료에 없는 수치·명령·식별자를 지어내지 않는다.

### 포함/제외 경계

판정 질문은 **"기술적 문제-해결인가?"** 입니다.

- 포함: 일반 dev 이슈, AI 엔지니어링(OCR/VLM/RAG/에이전트), **그리고 고객 시스템 이슈도 포함** — 고객사 게이트웨이 정책처럼 특정 고객에 묶인 것도 그 고객 후속 담당자에게는 최고 가치입니다.
- 제외: 비기술 판단(채용·HR·일정·견적), 단순 작업 로그(문제-해결 구조 없음) → `excluded.md`

## 안전장치

1. **자격증명 게이트** (결정론적 regex, `apply-knowledge.py`의 단일 관문 — 카드·APPEND 전부 통과): 12종 포맷(Anthropic/OpenAI/Google/GitHub/GitLab/Slack/AWS/JWT/PEM/URI `user:pass@`/일반 `api_key= 값`) 중 하나라도 걸리면 **run 전체 거부**(exit 3, 커서 미전진, **내용은 로그에도 남기지 않음**). 오탐 방지를 위해 `sk-` 계열은 앞 경계로 앵커링되어 있습니다(`task-management-…` 같은 슬러그가 걸려 영구 정지하던 회귀의 수정).
2. **프롬프트 인젝션 방어**: 일지 본문의 `===`/`▼▼▼` 마커 라인은 이스케이프되어 추출기 블록을 위조할 수 없고, 양 단계 프롬프트에 신뢰 경계(자료는 데이터, 지시 아님)를 명시
3. **출력 형식 가드**: 유효 마커 없는 LLM 출력(에러 메시지 등)은 기록 거부, 커서 미전진 → 다음 주 재시도
4. **테스트 훅 봉인**: `KNOWLEDGE_LLM_CMD`는 `KNOWLEDGE_ALLOW_CMD_OVERRIDE=1`과 함께일 때만 동작
5. **소스 격리**: `private/`는 activity 동기화·지식 추출 어느 쪽의 입력도 아님 (양쪽 테스트로 고정)

### 잔여 위험 (정직한 한계)

- **PII 리댁션이 없습니다.** 이는 의도된 설계입니다(사내 내부용). 이 레포를 외부 공개하거나 사외 인원에게 열면 그 순간 위 전제가 깨집니다 — **원격 접근 권한이 유일한 경계**입니다.
- **고객 제출 문서를 여기서 뽑을 때는 사람이 걸러야 합니다.** 리포트 dry-run에서 `activity/` 원문에 실명+사번, 내부 IP·호스트, GitLab MR 경로, 환경변수명, 그리고 우리가 고친 취약점 이력이 그대로 있음이 확인됐습니다. `/bc-knowledge` 스킬이 경고는 하지만 **자동 정제 도구는 없습니다** — 한 번 놓치면 사번이 고객 문서에 들어갑니다.
- **16자 미만 저엔트로피 비밀**(`password = hunter2`)과 **비표준 벤더 토큰의 bare 노출**은 오탐 임계 아래라 미커버
- **프롬프트 인젝션에 의한 내용 왜곡**(카드 날조)은 잔존 — 자격증명 게이트를 우회할 수는 없어 유출이 아닌 무결성 리스크
- `config.json`이 push 목적지를 결정하므로 **config.json 무결성이 보안 요소**

## 증분·동시성 동작

- **커서**: `<knowledge_repo>/.extract-cursor` (gitignored, 머신별) — 이전 실행 이후 mtime이 변한 일지만. **적용+커밋 성공 후에만 전진**
- **병합**: 기존 카드 목록(INDEX)을 2단계 프롬프트에 제공 → 같은 원인이면 `APPEND`(사례 누적). 같은 슬러그의 NEW는 자동 APPEND 강등 (덮어쓰기 불가)
- **팀 동시 push**: 실행 시작 시 `pull --rebase` 선동기화(미완 rebase 감지 시 중단). push 실패는 로그에 명시적 ERROR — 커밋은 로컬 보존되고 다음 실행의 선동기화가 배달

## ⚠️ 재추출은 손실적 — 정상 운영은 증분(append)

주간 정상 운영은 증분이라 **카드를 잃지 않습니다.** 반면 **전체 재추출(wipe 후 재생성)은 손실적**입니다 — LLM 판단이 비결정적이라 검증된 좋은 카드가 드롭될 수 있습니다(실측: private-GitLab-404 카드가 재추출에서 사라져 팀원 검색이 SOLVED→미착지로 회귀). 프롬프트를 개선했다고 전체를 wipe하지 마세요. 개선은 **다음 증분부터** 새 카드에 적용됩니다. 굳이 해야 하면 재추출 전 백업 후 드롭된 카드를 복원하세요(`git show <seed>:cards/<슬러그>.md`).

## 운영 런북

| 증상 | 대응 |
|---|---|
| `ERROR: pre-sync pull --rebase failed` | 진짜 텍스트 충돌. `cd <knowledge_repo>` → `git pull --rebase` → 수동 해결(INDEX.md는 어느 쪽이든 무방, 다음 추출이 재생성) → `git push`. 해결 전까지 해당 멤버 추출은 안전하게 중단됨 |
| `ERROR: git push failed` / `stranded commit(s)` | 커밋은 로컬 보존. 다음 실행의 pre-sync가 자동 배달. 반복되면 원격 권한·네트워크 확인 |
| 카드가 얕다 (근거 없음) | 로그의 `N deep + M shallow`를 확인. shallow가 많으면 트랜스크립트가 정리된 것 — 오래된 세션은 복구 불가, 최근 것부터 개선됨 |
| 같은 주에 두 멤버가 같은 문제를 카드화(슬러그 중복) | 한 카드로 수동 병합 후 커밋. **예방: 멤버별 실행 요일 분산** |
| 도구 레포 이동 후 무동작 | 훅·스킬이 절대경로 — `setup-team-member.sh` 재실행 |
| (분기 1회) 자격증명 패턴 점검 | `apply-knowledge.py`의 `SECRET_RE`에 신규 벤더 토큰 포맷 추가 검토 — 무인 push 파이프라인의 유일한 정기 관리 항목 |
